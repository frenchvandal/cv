## 為什麼用磁碟上的 Markdown

履歷住在 `src/translations.ts`
裡,和介面文案放在一起:一份手工譯成七種語言的文件,每一條字串都由程式碼測量並調整。文章正相反——長篇散文,既不受型別檢查,也不被測量,而且還會不斷增加。我不希望每發表一篇,打包體積就長一截,更不希望一個筆誤讓編譯失敗。於是內容住在磁碟上,由建置在預先算繪時讀取。程式碼歸程式碼,散文歸散文。

## 檔案系統就是資料

一篇文章的位址只有兩段:資料夾是
slug,檔名是語言。`content/posts/comment-ecrire-un-article/zh-hant.md`
就是你正在讀的這一頁;旁邊的 `en.md`
是它的英文版。沒有對照表,也沒有註冊表:翻譯就是在旁邊放一個檔案,撤掉一種語言就是刪掉一個檔案。那條規則——一篇文章存在於一到
n
種語言中,每份索引只列出自己這門語言裡確實存在的——不可能因為遺忘而被違反。`shanghai-note`
就是明證:它只有中文,所以西班牙文讀者永遠不會在自己的索引裡看到它;而從中文頁面出發,語言切換器會把人送到各語言的索引,而不是一個死連結。這篇文章則相反,七種語言俱全。

## 無相依的算繪

算繪用的是 `Bun.markdown`,Bun 內建的 GFM
引擎:整個專案一共只有兩個相依套件,部落格一個算繪相依也沒有再添。分兩步——`Bun.markdown.html()`
產出 HTML,隨後 `HTMLRewriter` 補上它不做的事:標題錨點、外部連結的
`rel`、可橫向捲動的表格、延遲載入的圖片,以及中文片段的 `lang` 標記。

## 英文在根目錄

英文住在網站根目錄,其餘每種語言各佔一個資料夾:英文是 `/blog/…`,這一版是
`/zh-hant/blog/…`。資源路徑按每一頁的深度計算,始終保持相對:`dist/`
可以原封不動地放到任何前綴之下,不必重新建置。只有做搜尋引擎最佳化的絕對 URL
會在部署時接上網域。

## 那道防線,不多也不少

`Bun.markdown` 會放過原始
HTML。逐個封堵已知標籤就是一份黑名單,從結構上說永遠是開著的;所以建置用的是一份封閉的白名單:只有合法
Markdown 會產出的標籤才能通過,其餘一律拒絕,無論是否見過。任何 `on…`
屬性都過不去。每個 `href` 或 `src` 在實體解碼、並剔除足以偽裝 `javascript:`
的控制字元之後,必須是
`http`、`https`、`mailto`,或者乾脆是相對路徑;沒能解析的實體一律拒絕,因為瀏覽器可是會解析它的。

它不保證的是:既非事件處理器也非 URL
的屬性不受檢查。這不是一個通用的淨化器,而是圍著「一篇文章可以產出什麼」築起的一道籬笆——而這篇文章本身就通過了自己的過濾器,這正是要點。

## 手冊

寫一篇文章,就是建一個檔案:

```text
content/posts/<slug>/<lang>.md
```

slug
由小寫字母、數字和連字號組成。有些名字是保留的,因為它們已經指向網站的某個檔案或資料夾:`assets`、`blog`、`cv`、`index`、`404`、`robots`、`sitemap`、`feed`、`og-image`,以及各語言代碼——一篇叫
`zh-hant` 的文章會蓋掉該語言的資料夾。

frontmatter 是 YAML,讀它的是 `Bun.YAML.parse`——語法由 Bun
負責,所以你寫的就是你在別處一直寫的那種 YAML。建置負責的是契約:`title` 和 `date`
必填,其餘可選,任何未知或重複的鍵都會被拒絕,並指名是哪個檔案。一個完整的例子:

```text
---
title: 怎樣寫一篇文章
date: 2026-08-09
summary: 這篇文章承諾了什麼,一句話說清。
tags: [meta, web]
---
```

逐欄位來說:`date` 是一個真實存在的 `YYYY-MM-DD`
日期——二月三十一日會被拒絕;`summary` 若不寫,會從內文推導;`tags` 寫成
`[a, b]`;`draft: true` 會把文章排除在外,除非 `DRAFTS=1`;`updated`
用來標註修訂日期。

想按真實 URL 閱讀文章——開發伺服器並不知道部落格的那些位址:

```bash
bun run preview           # 建置,然後在 http://localhost:4173 提供服務
PORT=8080 bun run preview # 換一個連接埠
DRAFTS=1 bun run preview  # 包含草稿
```

字型不必操心:推送到 `main` 之後,有一個工作流程會重新為網站的 Noto
產生子集並提交檔案。若想在推送前就看到文章真實的字形:

```bash
bun run fonts:update
```

子集裡缺一個字形,頁面上就是一個豆腐塊;而建置會拒絕產出涵蓋不全的
`dist/`——所以忘記這一步是一次響亮的失敗,絕不會變成讀者螢幕上的意外。

最後是 `zh-hk` 的規則:寫好 `zh-hant.md`
就夠了——香港版由網站的詞彙表從台灣版投影而來,而明確的 `zh-hk.md`
優先。乾巴巴的慣例住在 `AGENTS.md` 裡;這篇文章是敘述,那個檔案是參考。
